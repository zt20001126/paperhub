# 用户登录注册功能 PRD

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 产品名称 | PaperHub |
| 模块名称 | 用户登录注册 |
| 文档类型 | PRD |
| 当前阶段 | 基础功能已实现，进入优化阶段 |
| 目标用户 | 普通注册用户、系统管理员、后端维护人员 |

## 2. 背景说明

PaperHub 当前已经基本实现用户登录和注册功能。注册仅支持邮箱注册，用户需要输入邮箱、图形验证码、邮箱验证码、密码和确认密码；登录时需要输入账号、密码和图形验证码。

现阶段需要对登录注册功能进行优化，重点包括验证码存储、安全校验、过期策略、防刷限制、用户体验和接口行为一致性。其中邮箱验证码应放入 Redis；图形验证码也应使用服务端临时存储，推荐同样放入 Redis，并通过 `captchaId` 与验证码答案进行绑定。

## 3. 产品目标

1. 提升注册和登录流程的安全性，降低暴力破解、验证码撞库和邮箱验证码滥发风险。
2. 将验证码类短生命周期数据从本地内存或数据库中剥离，统一放入 Redis 管理。
3. 明确注册、登录、发送邮箱验证码、获取图形验证码的业务规则和异常提示。
4. 保证前后端交互流程清晰，用户能够顺畅完成注册和登录。
5. 为后续扩展短信登录、找回密码、第三方登录等认证能力预留一致的验证码模型。

## 4. 范围说明

### 4.1 本期包含

- 邮箱注册。
- 注册时校验图形验证码。
- 注册时发送并校验邮箱验证码。
- 注册时两次密码一致性校验。
- 登录时校验账号、密码和图形验证码。
- 邮箱验证码存入 Redis。
- 图形验证码存入 Redis。
- 验证码过期、使用后删除、错误次数限制。
- 邮箱验证码发送频率限制。
- 登录失败次数限制。
- 基础接口返回规范和前端交互提示。

### 4.2 本期不包含

- 手机号注册或短信验证码。
- 第三方登录。
- 忘记密码和重置密码。
- 多因素认证。
- 后台用户管理。
- 邮箱换绑。

## 5. 用户角色

| 角色 | 说明 |
| --- | --- |
| 未登录用户 | 可以访问登录页、注册页，完成注册和登录 |
| 已注册用户 | 可以使用邮箱和密码登录系统 |
| 系统维护人员 | 关注验证码配置、Redis 状态、邮件发送状态和异常日志 |

## 6. 核心业务流程

## 6.1 注册流程

1. 用户进入注册页面。
2. 前端请求图形验证码接口，获取 `captchaId` 和验证码图片。
3. 用户输入邮箱、图形验证码、邮箱验证码、密码、确认密码。
4. 用户点击发送邮箱验证码。
5. 后端校验邮箱格式、邮箱是否已注册、图形验证码是否正确。
6. 图形验证码校验通过后，后端生成邮箱验证码并发送到用户邮箱。
7. 邮箱验证码写入 Redis，并设置有效期。
8. 用户提交注册。
9. 后端校验邮箱、邮箱验证码、密码规则、两次密码是否一致。
10. 校验通过后创建用户，密码使用安全哈希算法加密保存。
11. 注册成功后，删除已使用的邮箱验证码。

## 6.2 登录流程

1. 用户进入登录页面。
2. 前端请求图形验证码接口，获取 `captchaId` 和验证码图片。
3. 用户输入账号、密码和图形验证码。
4. 用户提交登录。
5. 后端校验图形验证码。
6. 图形验证码校验通过后，后端校验账号和密码。
7. 登录成功后返回登录态信息。
8. 登录成功或图形验证码校验成功后，应删除本次使用的图形验证码，避免重复使用。

## 6.3 图形验证码刷新流程

1. 用户点击刷新验证码。
2. 前端重新请求图形验证码接口。
3. 后端生成新的 `captchaId`、验证码答案和验证码图片。
4. 后端将验证码答案写入 Redis。
5. 前端替换页面上的验证码图片和 `captchaId`。

## 7. 功能需求

### 7.1 获取图形验证码

| 项目 | 说明 |
| --- | --- |
| 触发场景 | 打开登录页、打开注册页、用户点击刷新验证码 |
| 输入 | 无 |
| 输出 | `captchaId`、验证码图片、过期时间 |
| 存储 | Redis |
| 有效期 | 建议 5 分钟 |
| 使用次数 | 单次有效 |

业务规则：

- 每次请求图形验证码都生成新的 `captchaId`。
- `captchaId` 应使用 UUID、随机字符串或其他不可预测 ID。
- Redis 只保存验证码答案，不保存图片内容。
- 验证码答案建议统一转为小写存储和比较，避免大小写导致误判。
- 图形验证码校验成功、过期或错误次数超限后应删除。
- 图形验证码错误时，前端应提示用户刷新或重新输入。

### 7.2 发送邮箱验证码

| 项目 | 说明 |
| --- | --- |
| 触发场景 | 注册页点击发送邮箱验证码 |
| 输入 | 邮箱、`captchaId`、图形验证码 |
| 输出 | 发送成功或失败提示 |
| 存储 | Redis |
| 有效期 | 建议 5 分钟 |
| 发送间隔 | 建议同一邮箱 60 秒内只能发送 1 次 |

业务规则：

- 邮箱不能为空，必须符合邮箱格式。
- 邮箱已注册时，不允许发送注册验证码。
- 发送邮箱验证码前必须先校验图形验证码。
- 图形验证码校验通过后，才允许发送邮箱验证码。
- 邮箱验证码为 6 位数字或其他固定长度随机码。
- 同一邮箱在有效期内重复发送时，可覆盖旧验证码，也可以拒绝发送；推荐覆盖旧验证码并刷新有效期。
- 邮箱验证码发送成功后，前端按钮进入倒计时状态。
- 邮件发送失败时，不应写入可用验证码，避免用户收到旧状态提示。

### 7.3 用户注册

| 项目 | 说明 |
| --- | --- |
| 触发场景 | 用户提交注册表单 |
| 输入 | 邮箱、邮箱验证码、密码、确认密码 |
| 输出 | 注册成功或失败提示 |
| 依赖 | Redis 中的邮箱验证码 |

业务规则：

- 仅支持邮箱注册。
- 邮箱不能为空，必须符合邮箱格式。
- 邮箱必须未被注册。
- 邮箱验证码不能为空，必须与 Redis 中保存的验证码一致。
- 邮箱验证码过期时，提示用户重新获取。
- 密码和确认密码不能为空。
- 两次输入的密码必须一致。
- 密码必须满足基础复杂度要求，建议至少 8 位，包含字母和数字。
- 用户密码必须使用 BCrypt 等安全哈希算法保存，禁止明文保存。
- 注册成功后删除该邮箱对应的邮箱验证码。
- 注册失败时不应泄露过多系统细节。

### 7.4 用户登录

| 项目 | 说明 |
| --- | --- |
| 触发场景 | 用户提交登录表单 |
| 输入 | 账号、密码、`captchaId`、图形验证码 |
| 输出 | 登录成功信息或失败提示 |
| 依赖 | Redis 中的图形验证码 |

业务规则：

- 账号不能为空。当前账号可使用邮箱字段。
- 密码不能为空。
- 图形验证码不能为空。
- 图形验证码必须先于账号密码校验，减少无效登录请求进入密码校验逻辑。
- 图形验证码错误、过期或不存在时，登录失败。
- 账号不存在或密码错误时，返回统一提示，例如“账号或密码错误”。
- 登录成功后删除图形验证码。
- 登录失败达到限制次数时，应进行临时锁定或提高验证要求。

## 8. Redis 设计

### 8.1 图形验证码 Redis 设计

推荐将图形验证码存储在 Redis 中，不建议放在前端、本地变量或数据库中。

推荐 Key：

```text
auth:captcha:{captchaId}
```

推荐 Value：

```json
{
  "code": "a7k9",
  "scene": "login",
  "failCount": 0
}
```

简化实现也可以只保存验证码答案：

```text
a7k9
```

推荐 TTL：

```text
300 秒
```

说明：

- 图形验证码是短生命周期、一次性校验数据，Redis 比数据库更适合。
- 如果后端是单机部署，也可以使用本地缓存；但为支持多实例部署和后续扩展，推荐统一使用 Redis。
- 不应将图形验证码答案返回给前端。
- 校验成功后应立即删除 Redis Key。

### 8.2 邮箱验证码 Redis 设计

推荐 Key：

```text
auth:email-code:register:{email}
```

推荐 Value：

```json
{
  "code": "123456",
  "failCount": 0
}
```

推荐 TTL：

```text
300 秒
```

发送频率限制 Key：

```text
auth:email-code:cooldown:register:{email}
```

推荐 TTL：

```text
60 秒
```

说明：

- 邮箱验证码只用于注册场景时，Key 中应包含 `register`，避免未来找回密码等场景互相污染。
- 邮箱验证码校验成功后应立即删除。
- 验证码错误次数达到上限后应删除验证码，并要求用户重新发送。

### 8.3 登录失败限制 Redis 设计

推荐 Key：

```text
auth:login:fail:{account}
```

推荐 TTL：

```text
15 分钟
```

业务规则：

- 同一账号连续登录失败达到 5 次后，建议锁定 15 分钟。
- 锁定期间直接返回“登录失败次数过多，请稍后再试”。
- 登录成功后清除失败次数。
- 可结合 IP 增加限制，例如 `auth:login:fail-ip:{ip}`。

## 9. 接口需求

### 9.1 获取图形验证码

```text
GET /api/auth/captcha
```

返回：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `captchaId` | `string` | 图形验证码 ID |
| `imageBase64` | `string` | 图片 Base64 |
| `expiresInSeconds` | `number` | 过期秒数 |

### 9.2 发送邮箱验证码

```text
POST /api/auth/send-code
```

请求：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `email` | `string` | 是 | 注册邮箱 |
| `captchaId` | `string` | 是 | 图形验证码 ID |
| `captchaCode` | `string` | 是 | 用户输入的图形验证码 |

返回：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `success` | `boolean` | 是否成功 |
| `message` | `string` | 提示信息 |

### 9.3 注册

```text
POST /api/auth/register
```

请求：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `email` | `string` | 是 | 注册邮箱 |
| `emailCode` | `string` | 是 | 邮箱验证码 |
| `password` | `string` | 是 | 密码 |
| `confirmPassword` | `string` | 是 | 确认密码 |

返回：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `success` | `boolean` | 是否成功 |
| `message` | `string` | 提示信息 |

### 9.4 登录

```text
POST /api/auth/login
```

请求：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `account` | `string` | 是 | 登录账号，当前为邮箱 |
| `password` | `string` | 是 | 密码 |
| `captchaId` | `string` | 是 | 图形验证码 ID |
| `captchaCode` | `string` | 是 | 用户输入的图形验证码 |

返回：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `success` | `boolean` | 是否成功 |
| `message` | `string` | 提示信息 |
| `data` | `object` | 登录成功后的用户信息或令牌 |

## 12. 安全要求

1. 验证码答案禁止返回前端。
2. 图形验证码和邮箱验证码都必须设置过期时间。
3. 验证码校验成功后必须删除，避免重复使用。
4. 邮箱验证码发送必须有限流策略。
5. 登录失败必须有限制策略，防止暴力破解。
6. 密码必须加密存储，禁止明文保存。
7. 登录错误提示应避免暴露账号是否存在。
8. 邮箱验证码错误次数应有限制，建议最多 5 次。
9. 图形验证码错误次数应有限制，建议最多 5 次。
10. 接口日志中禁止打印明文密码、邮箱验证码和图形验证码答案。

## 13. 配置项建议

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `captcha.expire-seconds` | `300` | 图形验证码有效期 |
| `captcha.max-fail-count` | `5` | 图形验证码最大错误次数 |
| `email-code.expire-seconds` | `300` | 邮箱验证码有效期 |
| `email-code.cooldown-seconds` | `60` | 同一邮箱发送间隔 |
| `email-code.max-fail-count` | `5` | 邮箱验证码最大错误次数 |
| `login.max-fail-count` | `5` | 登录最大失败次数 |
| `login.lock-seconds` | `900` | 登录锁定时间 |
| `password.min-length` | `8` | 密码最小长度 |

## 14. 数据库要求

用户表至少需要支持以下字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 用户 ID |
| `email` | 邮箱，唯一 |
| `password` | 加密后的密码 |
| `status` | 用户状态 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

说明：

- 邮箱字段必须加唯一索引。
- 密码字段只保存加密结果。
- 验证码不需要持久化到数据库。

## 15. 非功能需求

### 15.1 性能

- 验证码读写应在 Redis 中完成，接口响应应保持在可接受范围内。
- 邮件发送较慢时，可考虑异步发送；本期如果保持同步发送，需要保证异常处理清晰。

### 15.2 可用性

- Redis 不可用时，登录注册相关验证码能力不可用，应返回友好提示。
- 邮件服务不可用时，应返回邮件发送失败提示。

### 15.3 可维护性

- 验证码能力应封装为独立服务，例如 `CaptchaService`、`EmailCodeService`。
- Redis Key 应集中管理，避免散落在业务代码中。
- 验证码场景应使用枚举或常量区分，例如 `REGISTER`、`LOGIN`。

## 16. 验收标准

1. 注册页可以正常获取并刷新图形验证码。
2. 发送邮箱验证码前必须校验图形验证码。
3. 图形验证码错误、过期或不存在时，不能发送邮箱验证码。
4. 邮箱验证码成功发送后写入 Redis，并具备过期时间。
5. 图形验证码写入 Redis，并具备过期时间。
6. 注册时必须校验邮箱验证码。
7. 注册时密码和确认密码必须一致。
8. 注册成功后，邮箱验证码从 Redis 删除。
9. 登录时必须校验图形验证码。
10. 登录成功后，图形验证码从 Redis 删除。
11. 邮箱验证码发送频率限制生效。
12. 验证码错误次数限制生效。
13. 登录失败次数限制生效。
14. 密码在数据库中不是明文。
15. 所有异常场景都有明确、友好的提示。
